# Changelog

측정으로 뒷받침된 변경만 기록합니다. 근거가 된 수치를 함께 남기는 이유는, 그
수치를 다시 얻는 데 시간이 오래 걸리기 때문입니다.

## v3.2 — 2026-08-18

### 코드 공개

`github.com/mac999/corpusbench` 로 공개했습니다. 도구 이름과 데이터셋 이름을
분리했습니다 — 파이프라인 자체(문서에서 사실 채굴 → 홀드아웃·probe 생성 →
closed/open 채점 → 유의성 검정)는 도메인과 무관하므로 `corpusbench`, 한국 건설
표준으로 만든 레퍼런스 데이터셋은 기존대로 `kcbench` 입니다. 코드의
`BENCHMARK_NAME` 은 후자를 가리키므로 건드리지 않았습니다. 빌드된 문항에
`kcbench-item-v2` 가 박혀 있어서, 바꾸려면 재빌드가 필요합니다.

공개 범위는 코드와 평가셋입니다. track 1 청크(13MB)와 학습 split(84MB)은 원문에서
가깝게 파생돼 재배포가 라이선스 문제라 제외했고, 빌드 스크립트로 재생성합니다.
`data/runs/` 도 뺐습니다 — 채점 결과물이지 벤치마크가 아니고, smoke 실행이 섞여
있었습니다. 기준선 수치는 README 표와 이 파일에 남습니다.

### 중단된 실행의 재개

평가가 죽으면 처음부터 다시 돌려야 했습니다. evaluate.py 가 트랙이 끝날 때만
파일을 쓰기 때문인데, probe 400문항이 두 번 연속 중간에 끊기면서 그때마다 몇
시간을 버렸습니다.

문항 단위 저널을 붙였습니다. 채점된 항목은 즉시 `data/runs/.ckpt/<tag>-<track>.jsonl`
에 flush + fsync 로 적히고, 다시 시작하면 이미 있는 항목을 건너뜁니다. 트랙이
점수를 쓰면 저널은 지워집니다. 세 가지를 지켰습니다:

- **빈 응답은 저널에 넣지 않습니다.** 서버가 죽은 동안 만들어진 기록이 살아남으면
  재시작해도 오답으로 굳습니다. dapt-probe 폐기가 정확히 그 사고였습니다.
- **설정이 바뀌면 저널을 버립니다.** 모델·언어·repeats·closed_book·문항수를 헤더에
  적어두고 하나라도 다르면 `.stale` 로 밀어냅니다.
- **깨진 마지막 줄은 무시합니다.** kill -9 가 남기는 흔적입니다.

빈 응답 가드도 추가했습니다(`max_consecutive_empty`, 기본 25). 기존
`max_consecutive_failures` 는 예외만 잡는데, 200 을 돌려주면서 본문이 비는 서버는
호출이 전부 "성공"하고 답이 전부 오답이 됩니다. 같은 사고의 두 번째 신호입니다.

재시도는 `run_resumable.sh` 가 맡습니다. 재시도했는데 새로 채점된 항목이 0개면
정체로 세고, 3회 정체하면 멈춥니다 — 고장난 실행이 점수로 남는 것보다 낫습니다.

검증: limit 12 로 돌리다 5문항에서 kill -9 → 저널 5건 보존, 점수 파일 미생성 →
재실행 시 "resuming, 5 of 400" 후 12문항 완주, 저널 삭제. repeats 를 바꿔 재실행하면
설정 불일치로 저널 폐기.

### repeats 3 → 1

`temperature` 가 0 인데 문항마다 3회씩 생성하고 있었습니다. 그리디 디코딩은
결정적이라 세 번 모두 같은 답이 나옵니다. base probe 실행(`v3-probe-closed.json`)
의 점수 560개를 전부 확인한 결과 **3회가 갈린 항목이 하나도 없습니다.** 3배
비용에 정보량은 0입니다.

`config.json` 의 `eval.repeats` 를 1로 낮췄습니다. 측정치: dapt-probe 가 문항당
36초에서 18초로 떨어졌고, probe + track 2 closed 합계가 약 8시간에서 2.7시간이
됐습니다. 점수는 같은 값이 나오므로 기존 기준선과 그대로 비교됩니다. 샘플링 분산을
보고 싶으면 temperature 와 repeats 를 함께 올려야 합니다.

### GPU 클럭 복구

8/17 강제종료 이후 부하 시 SM 클럭이 630MHz 에 고착하고 `SW Power Capping` 이
계속 잡혀 있었습니다. 드라이버 레벨 조작(-lgc/-rgc/--gpu-reset)도, 일반 재부팅도
듣지 않았고, 전원 케이블을 30초 이상 분리한 콜드 부팅에서 풀렸습니다. 대기전원이
남아 있으면 EC/SOC 전력예산 상태가 리셋되지 않습니다.

| 항목 | 고착 시 | 복구 후 |
|---|---:|---:|
| SM 클럭 (부하) | 624~630 MHz | 2190~2561 MHz |
| 전력 | 17.5 W | 92 W |
| bf16 8192³ matmul | 3.4 TFLOPS | 10.5 TFLOPS |
| ollama 생성 | — | 43.1 tok/s |

matmul 이 10.5 TFLOPS 에 머무는 것은 별개 문제입니다. GB10 은 compute capability
12.1 인데 설치된 torch 2.11.0+cu128 은 sm_80/90/100/120 커널만 담고 있습니다.
클럭당 효율이 고착 시와 같으므로(3.5배 클럭 → 3.1배 성능) 전력 문제가 아니라
원래부터 있던 한계입니다. ollama 는 llama.cpp 경로라 영향을 받지 않습니다.

### dapt-probe 실행 결과 폐기

18:49 에 기록된 `data/runs/dapt-probe.json` (probe_score 0.013) 을 버렸습니다.
재부팅으로 ollama 가 내려가는 동안 evaluate.py 가 계속 돌면서 150~400번 문항이
전부 생성 실패로 채워졌습니다 — 로그에 `Connection refused` 가 250줄 남아 있고,
125/400 까지의 정상 구간과 나머지가 한 파일에 섞였습니다. 점수 0.013 은 모델
성능이 아니라 빈 응답의 비율입니다.

### 연속 생성 실패 시 트랙 중단

`evaluate.py` 는 트랙이 끝날 때만 파일을 쓰므로 중간 실패를 감지할 방법이
없었습니다. 서버가 사라지면 남은 문항이 전부 빈 응답으로 채점되고, 트랙은
정상 종료하면서 "빈 응답 비율"을 점수로 기록합니다.

`run_qa` 에 연속 실패 카운터를 넣고 `eval.max_consecutive_failures` (기본 20) 를
넘으면 RuntimeError 로 중단시킵니다. 연속 횟수를 기준으로 잡은 이유는, 간헐적
타임아웃은 성공 한 번에 카운터가 초기화되지만 죽은 서버는 초기화되지 않기
때문입니다. 20회는 repeats=3 기준 약 7문항 분량입니다.

ollama 를 내린 채로 확인: `--tracks probe --limit 30` 이 7/30 문항에서 중단되고
결과 파일을 남기지 않습니다.

8/17 강제종료 이후 GPU 가 부하 시 630MHz / 17.5W 에 고착돼 있습니다. 정상
재부팅으로 복구된다고 봤으나 8/18 재부팅 후에도 동일합니다.

| 항목 | 값 |
|---|---|

클럭에서의 예상은 400문항 1시간 이내였습니다.

### uc1 nameset·uc5 증설

80% 판정의 검출력이 부족한 두 트랙을 늘렸습니다(계산은 STANDARDS_REVIEW.md).

- **uc1 nameset 28 → 72.** 병목은 두 가지였습니다: 문서당 목록 1개 제한
  (`nameset_max_per_doc` 설정으로 승격, 3으로), 이름 패턴 필터(카테고리 전체
  269문서로 확대). 85개를 목표로 했으나 채굴기 규칙을 통과하는 목록이 72개가
  전부 — 남은 한계는 코퍼스입니다. CI 반폭 ±18%p → ±11%p.
- **uc5 46 → 118.** `min_items_per_list` 4 → 3(3항 목록에서 1개 제거도 유효한
  문항), 패턴 필터 제거. CI 반폭 ±12%p → ±7%p.
- uc1 합계 157문항(홀드아웃 100), uc5 118문항(홀드아웃 22). 문항 집합이
  바뀌었으므로 기준선을 재측정했습니다(`v3.1-uc-qwen3-8b--{open,closed}`):

| 트랙 | 유형 | 문항 | open | closed |
|---|---|---:|---:|---:|
| uc1_safety | numeric | 85 | 0.953 | 0.176* |
| uc1_safety | nameset | 72 | 0.531 | 0.000* |
| uc5_incident | nameset | 118 | 0.660 | 0.022 |

\* closed 합산 0.082. uc5는 신규 문항이 더 어려워 open이 0.778 → 0.660으로
내려갔고, 손실의 주범은 precision(0.61) — 요구된 누락 조치 외의 항목까지
나열하는 경향입니다(recall 0.82). uc1 nameset은 0.415 → 0.531로 추정이
안정화됐습니다. 목록형 응답이 80% 목표 대비 실질 격차라는 진단은 유지되며,
이제 ±7~11%p 검출력으로 말할 수 있습니다.

### 프롬프트 언어 비율

에이전트 운용 언어가 한국어이므로 `eval.lang_mix`(기본 ko 0.8 / en 0.2, 4:1)와
`evaluate.py --lang mix` 를 추가했습니다. 문항 id 해시로 언어를 정하므로 같은
문항은 매 런 같은 언어로 물어, 전후 비교에 언어 변화가 섞이지 않습니다. 집계에
`by_lang` 분리가 붙습니다. 모든 문항이 ko/en 쌍을 이미 갖고 있어 데이터 재생성은
없습니다. 기존 기준선은 `--lang ko` 로 측정되었고 그 비교 체계는 그대로입니다.

## v3 — 2026-08-16

### 유스케이스 트랙 추가

에이전트의 다섯 유스케이스(안전 확인, 철근 검사, 현장↔BIM 비교, 규정 위반 조사,
사고 분석)를 벤치마크가 직접 재도록 `build_usecases.py` 와 config의 `usecases`
레지스트리를 추가했습니다. UC 하나 = config 엔트리 + (필요 시) builder 함수
하나. evaluate.py 는 레지스트리를 읽어 `--tracks uc` 로 채점하므로 코드 수정
없이 UC가 늘어납니다. 목표 지표는 RAG 장착 시 출력 정확도 80% 이상 — 검색이
조문을 건네주는 open book이 운용 측정입니다.

- **uc1_safety 112문항 / uc2_rebar_spec 150문항** — track 2 채굴기를 문서
  필터로 재사용. 최초 필터(작업지침류 이름 패턴)는 6·7문항밖에 내지 못해
  카테고리 전체로 넓혔습니다(03 안전 211문서, 01+02 기준·시방 52문서).
  안전 작업지침·시방서 대부분이 학습 측이므로 해당 문항은 probe와 같은
  `contamination: "intentional"` 표시를 갖고, 집계에 `by_split` 이 분리됩니다.
- **uc3_bim_site 48문항** — 홀드아웃 6개 IFC 모델의 `bim_site_comparison`(BIM
  렌더+현장사진 교차 판정)과 `progress_assessment`(기성 단계) 라벨 사용.
  라벨은 생성 시 주석이라 IFC 카탈로그보다 약한 근거이며 문항이 그렇게
  명시합니다. 비교 라벨은 mismatch로 치우쳐(15/24) 항상 mismatch만 답해도
  62%가 나오므로 `by_task` 분리 없이 읽으면 안 됩니다.
- **uc4_faithfulness 160문항 (교체 80 / 대조 80)** — 기존 closed book 채점에서
  6개 모델 전부 무응답률 0.0%로, 모르면 지어내는 것이 지배적 실패 모드였습니다.
  track 2 numeric 문항의 조문을 무관한 조문으로 바꾸고(정답 문자열이 교체
  조문에 없음을 검증, 잔존 0건) `자료 없음` 기권만 정답으로 칩니다. 대조
  문항이 절반이라 전부 기권하는 모델은 50%에 멈춥니다.
- **uc5_incident 46문항** — 실제 사고 사례 데이터가 코퍼스에 없어, 작업지침
  각 호 목록에서 일부 조치를 제외하고 "확인된 조치" 시나리오를 만든 뒤 누락
  조치를 묻습니다. 정답은 제외한 부분집합 그대로라 기계 검증이 됩니다.
- **퍼지 nameset 채점.** uc5 스모크에서 모델이 의미상 정답(`방수구역마다
  일제개방밸브 설치`)을 내고도 문자열 집합 비교로 0점이 됐습니다. 산문형
  답에는 `match_mode: "fuzzy"`(내용어 60% 커버리지, 1:1 그리디 매칭)를
  적용합니다. 같은 문항이 정확 일치 0.000 → 퍼지 0.667로, 80% 달성 가능
  기준이라는 요구와 정합합니다. track 2·3 채점은 그대로입니다.

  채점에서 무응답률 0.0%였던 같은 모델이, `자료 없음`을 지시문에 넣자 엉뚱한
  조문에서 95% 기권했습니다. 대조 문항 손실(0.838)의 대부분은 과잉 기권(10%)
  입니다. RAG 에이전트 프롬프트에 기권 지시를 넣는 것이 사실상 무료 안전
  장치라는 뜻입니다.
- **uc3은 라벨 신뢰도 문제가 실측으로 확인됐습니다.** 비교 과제에서 항상
  mismatch만 답하는 전략이 0.625인데 qwen3-vl:30b가 0.333입니다. 모델이
  라벨보다 나쁘다기보다 라벨 자체(생성 시 주석, `unknown` 7건 전부 오답 처리)
  가 채점 기준으로 약하다는 신호입니다. 사람 검수 전까지 uc3 점수는 방향
  지표로만 읽어야 합니다.

- **`think: false`.** 사고형 모델에서 이 옵션은 사고를 끄지 않고 **분리만 해제**합니다.

  섞이면 파인튜닝 전후 비교에서 하네스 결함이 성능 변화로 읽힙니다.

### 문항 생성 규칙

v1은 400문항 중 절반이 사람도 답할 수 없었습니다.

- **numeric.** 주어를 숫자 앞에서 역방향으로 자르되, 앞 절의 꼬리가 붙은 경우
  (`있는 유량측정장치를 펌프 정격토출량`), 괄호 불균형, 다른 계측값 포함, 절 경계
  침범, 부사형 종결, 동사구 이월(`졸업한 후는`), 표 파편(`4우수 5내구성 경과년수`),
  토큰 중간 시작(`·정격하중`)을 각각 거부합니다. 194 → 132문항.
- **동일 단위·한정어 처리.** v1은 주어 문자열이 다르기만 하면 통과시켜
  `펌프 정격토출량 150%` 와 `…를 펌프 정격토출량 175%` 를 함께 냈고, 모델이 175를
  답해 오답 처리됐습니다. 주어 품질 검사를 먼저 통과시킨 뒤 **주어가 서로 포함관계인
  경우만** 거부하도록 순서를 바꿔, 고압식/저압식처럼 구분 가능한 쌍은 살립니다.
- **nameset.** 질문 머리말을 청크 첫 줄 60자에서 뽑던 방식을 버리고, 목록을 예고하는
  도입 문장(`다음 각 호`, `다음과 같다`)을 요구합니다. 도입 문장이 없으면 조문 제목
  (`제9조(전원 등)`)을 식별자로 씁니다. 청크 끝까지 이어지는 목록(잘림), `<삭제>`
  항목, 1부터 시작하지 않는 번호 열은 거부. 206 → 42문항이지만 F1 0.021 → 0.608.
- **채점 정규화.** NFKC + 공백·문장부호 정규화 후 집합 비교. 원문 그대로를 요구하면
  지식이 아니라 전사 능력을 재게 됩니다.

### probe 세트

track 2가 무엇을 재고 있는지 확인하다 나온 문제입니다. 홀드아웃 문항 320개 중 주어와
정답이 **같은 학습 행에 함께 등장하는 것은 79개(25%)** 뿐입니다. 나머지 241개는
학습 데이터 어디에도 답이 없어서 파인튜닝으로 배울 수가 없습니다. 홀드아웃이 그
문서들을 뺐으니 당연한 결과지만, 이는 track 2가 **습득이 아니라 일반화**를 재고
있다는 뜻입니다.

`build_probe.py` 로 학습 측 문서에서 같은 miner를 돌려 400문항(numeric 320 /
nameset 80)을 만들었습니다. 검증 결과 **83%**가 학습 데이터에 답이 있습니다
(track 2는 25%). 두 세트가 다른 질문에 답합니다:

| 세트 | 출처 | 학습에 답 존재 | 답하는 질문 |
|---|---|---:|---|
| track 2 | 홀드아웃 문서 | 25% | 못 본 규정에 일반화하는가 |
| probe | 학습 문서 | 83% | 가르친 것을 습득했는가 |

오염이 의도적이므로 모든 행이 `split: "train"`, `contamination: "intentional"` 을
가집니다. probe 점수를 벤치마크 결과로 보고하면 안 됩니다.

이 발견 때문에 앞서 제시한 성공 기준(closed numeric 0.166 → 0.40)은 과도했습니다.
track 2의 현실적 상한은 학습 가능한 25%를 완전히 익히는 수준, 즉 0.25~0.30입니다.
